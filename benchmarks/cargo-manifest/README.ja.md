# Cargo マニフェスト更新の測定記録

[English](README.md)

2026-10-31 に測定しました。従来の Cargo レジストリ依存の更新は、使わない複数行テーブルの更新でも、パッケージ名入りの正規表現を毎回 6 個コンパイルしていました。git tag 更新も毎回 2 個をコンパイルしていました。パッケージ名を文字列で照合し、後続の構文だけを共有の `LazyLock<Regex>` で読むように変更しています。3 つの宣言形式の版解析・整形も共通化し、セクション名の借用、出力バッファの予約、対象外の宣言のソース確認を省く変更を加えました。

公開パーサ API、版の整形、ソース除外、依存・patch セクションの範囲、引用符、コメント、改行の扱いは保持しています。

## 条件

- Windows x86_64、AMD Ryzen 7 5700X、8 コア・16 論理プロセッサ。
- rustc 1.99.1（`58cf8f9c3`、LLVM 23.1.1）、MSVC ターゲット。前後とも基準コミット `5d0572d4e312797001783ce681473cc7d37f4542` と同じ依存・ツールチェーンを使用。`Cargo.lock`・`mise.toml`・計測コードの Git blob ID と実行ファイルの SHA-256 は英語版に記録しています。
- 両実装を `mise exec -- cargo build --release --locked --example manifest_update_bench` でビルド。release 設定は LTO・codegen-units=1・strip です。変更前は基準コミットのライブラリに、変更後と同じ拡張した計測コードを組み合わせました。
- `manifest_update_bench 1000 7 cargo` を実行。ケースごとに 100 回ウォームアップ後、1 サンプル 1,000 回を 7 サンプル測定。各実装を 2 プロセス、計 14 サンプルで比較しました。順序は before-a → after-a → after-b → before-b。測定中はビルドやテストを動かさず、この測定の CPU は固定していません。
- 依存 1・100・1,000 件の末尾 1 件だけを `^1.0.0` → `^2.3.4`、または tag `v1.0.0` → `v2.3.4` へ更新します。入力生成と検証は計測外です。全ケースで出力のバイト単位の一致を確認し、同名メタデータ・単一引用符・CRLF・最終行の改行なしを保持します。入力と期待する出力の TOML 解析も確認します。
- 確保回数・バイト数は別のウォームアップ後の 1 更新で集計し、時間計測中は集計を止めます。バイト数は再確保を含む要求量で、ピークメモリや常駐メモリではありません。
- 保存した CSV の改行は LF に統一し、Windows の出力から改行を変えても全フィールドが同一であることを確認しています。
- 対象はウォームアップ後のメモリ内書き換えです。初回の遅延初期化、ネットワーク、レジストリ応答の解析、ファイル書き込み、CLI 全体の時間は含みません。特に依存 1 件の数値は、初回起動で 1 件だけ更新する CLI の短縮率を示すものではありません。

## 結果

時間は 14 サンプルの中央値、単位は 1 更新の µs です。丸め前の中央値と最小・最大値は [comparison.csv](comparison.csv) にあります。

| ケース | 変更前 µs | 変更後 µs | 時間短縮率 | 確保要求回数 | 確保要求バイト数 |
|---|---:|---:|---:|---:|---:|
| 単純指定・依存 1 件 | 407.239 | 1.643 | 99.60% | 3,535 → 19 | 3,045,601 → 651 |
| 単純指定・依存 100 件 | 451.931 | 6.964 | 98.46% | 4,232 → 19 | 3,421,431 → 2,928 |
| 単純指定・依存 1,000 件 | 952.455 | 55.839 | 94.14% | 10,536 → 19 | 3,784,311 → 23,628 |
| inline table・依存 100 件 | 506.400 | 8.388 | 98.34% | 4,372 → 20 | 3,504,945 → 6,509 |
| dotted key・依存 100 件 | 488.484 | 8.261 | 98.31% | 4,386 → 21 | 3,509,414 → 3,883 |
| 複数行テーブル・依存 100 件 | 396.404 | 17.045 | 95.70% | 3,443 → 20 | 3,367,673 → 7,369 |
| git tag inline table・依存 100 件 | 183.617 | 5.118 | 97.21% | 1,716 → 7 | 1,196,337 → 9,221 |
| git tag dotted key・依存 100 件 | 192.753 | 7.890 | 95.91% | 1,928 → 10 | 1,196,232 → 7,628 |
| git tag 複数行テーブル・依存 100 件 | 157.098 | 12.160 | 92.26% | 1,429 → 7 | 1,124,474 → 9,987 |

Cargo の全ケースで前後の時間分布が重ならず、確保回数・バイト数も減りました。単純指定 1,000 件の確保要求バイト数は 99.38% 減少しました。残る 2 回の走査の時間は入力に比例しますが、単純指定の確保回数は依存数に比例する状態から一定になりました。

生データ: [before-a](before-a.csv)、[after-a](after-a.csv)、[after-b](after-b.csv)、[before-b](before-b.csv)。中央値は実装ごとの a・b をケース別にまとめ、14 個の `ns_per_update` を並べて中央 2 値を平均します。短縮率は `(1 - 変更後 / 変更前) * 100` です。

## 比較用の測定と探索段階

実装を変えていない JSON のケースも同じ計測ヘルパを使います。CPU を固定しない 14 サンプルの結果は [json-comparison.csv](json-comparison.csv)、生データは `json-{before,after}-{a,b}.csv` です。確保回数・バイト数は一致しました。時間の中央値は 3.37% の短縮から 6.21% の増加まであり、エスケープ付きキーでは前後の範囲が重ならないため、この測定だけでは時間の退行がないとは判断できません。

追加測定では、計測用プロセスとその子プロセスだけを論理 CPU 2（Windows の affinity mask `4`）に固定し、システム全体の設定は変えていません。同じ実行ファイルで 100 回ウォームアップ後、1 サンプル 5,000 回、各実装 2 プロセスの計 14 サンプルを、before-a → after-a → after-b → before-b の順に計測しました。ビルド・テストは並行実行していません。生データは `json-affinity-{before,after}-{a,b}.csv`、中央値と範囲は [json-affinity-comparison.csv](json-affinity-comparison.csv) です。

| JSON の比較用ケース | 変更前 µs | 変更後 µs | 時間短縮率 |
|---|---:|---:|---:|
| Node 依存 1 件 | 2.532 | 2.546 | -0.54% |
| Node 依存 100 件 | 21.310 | 21.779 | -2.20% |
| Node 依存 1,000 件 | 193.816 | 197.349 | -1.82% |
| Node エスケープ付きキー 100 件 | 34.949 | 35.354 | -1.16% |
| Bun 依存 100 件 | 37.513 | 37.876 | -0.97% |
| Composer 依存 1,000 件 | 94.647 | 90.262 | 4.63% |

Node の 100・1,000 件では時間の範囲が引き続き重ならず、ほかの Node・Bun の範囲は重なっています。JSON の確保回数・バイト数はすべて一致しました。小幅な時間差の原因は特定できていません。Cargo の 92〜99.6% の短縮と確保量削減に対して、この JSON の測定差も記録したうえで採用しています。全パーサで退行がないことや、CLI 全体の高速化は主張しません。

`exploratory/` は最終比較に含めません。a・b の CSV と比較表は最初の版更新だけを変えた実験で、大きい入力に対象外の行のソース確認が残り、3,016 回の確保がありました。`preliminary-source-filter.csv` は名前の照合を先に行って 19 回に減った確認です。最初の git tag の測定はソースを変えていなくても 4〜10% 遅く、毎回の正規表現 2 個のコンパイルも残っていたため、同じ改善を適用してこのコストを取り除きました。`preliminary-before.csv` は 100 回更新での初回基準値、同ディレクトリの JSON は初回の各実装 1 プロセス分です。

## 検証と点検での判断

- 追加した境界テスト 2 件は変更前後とも成功。Cargo パーサの全 86 テストで、名前の境界・ソース除外・複数宣言・target/workspace/patch の範囲・引用符・CRLF・対象がない場合を確認しました。追加ケースは不規則な空白・同じ接頭辞の別名・コメント・最終行の改行なしを含む出力全体を照合します。
- 最終のローカル `make ci` は Git Bash 経由で成功。整形確認、全ターゲットの警告をエラーにした clippy、2,850 テストが通過し、`make release` も成功しました。既定で無視されるテストは 1 件、Unix 限定ケースは今回のローカル Windows 実行では対象外です。
- 全体の AST 構造と主要な呼び出しを調べ、OSV 判定・共有レジストリのロック・install transaction の準備・パスの範囲制限・Git の引数/タイムアウト/伏字化・検証付きファイル置換を確認しました。`astro-sight context`・`impact`・`review --git` に未対応の呼び出し元・公開 API 変更・新たな未参照シンボルはありません。履歴上の同時変更候補は、ほかの言語のパーサや使い方の文書を今回変える根拠にはなりません。
- Cargo の重複していた整形経路を共通化し、`update_version` の複雑度は 17 → 11、`update_git_tag` は 10 → 8 になりました。大きい install/OSV の関数は復元・安全性の境界を維持しました。内部で使われない公開 API `enforce_lock_age_rust` も保持しています。全パーサと writer のガードに影響する一括書き換え API は、残る走査時間に対して変更範囲が広いため今回導入していません。
- 開始時はクリーンな `main` で同期済み、退避や追加の取り込みは不要でした。`mise exec -- depup --install --include-pinned` はライブラリ依存 22 件と Rust ツールチェーンを更新不要と判定し、`Cargo.toml`・`Cargo.lock`・`mise.toml` は変えていません。開始時と実装中の GitHub open Issue は 0 件で、再現できる新規製品不具合も見つかりませんでした。
- README と開発文書は英語・日本語の両方に計測コマンドと Git Bash/PowerShell の検査手順を追記しました。確認したファイル置換処理の説明コメント 2 件は、コードを変えず日本語にしました。
- `/Users/owa/GitHub/mac-shell/shell/link_agent.md.sh` は Windows に存在せず、ローカルの Windows スクリプト名にも同等のものを確認できなかったため未実行です。`CLAUDE.md` は Git 上ではシンボリックリンク、チェックアウト上では通常ファイルのため、編集・置き換えをせず保持しました。
