# 依存の確認の並列度の測定記録

[English](README.md)

2026-11-13 に測定しました。マニフェストごとの依存の確認 (版の一覧の取得・判定・OSV の照会) の並列度の上限 `MAX_VERSION_CHECK_CONCURRENCY` を 4 から 16 に上げました。版の一覧の取得はレジストリ別のセマフォ (crates.io は 8、ほかは 10) が別に抑えるので、この上限が主に決めるのは、更新候補ごとの OSV の問い合わせが重なる数です。上限 4 では、60 件のマニフェストの確認が OSV の往復を 15 段待っていました。

## 条件

- Windows x86_64、AMD Ryzen 7 5700X、8 コア・16 論理プロセッサ。rustc 1.99.1 (`58cf8f9c3`)、MSVC ターゲット、`cargo build --release --locked` (LTO・codegen-units=1・strip)。
- 変更前は点検中の作業コピー (`fb72ab3`)、変更後はその上で上限だけを 16 にしたものです。実行ファイルの SHA-256 は、変更前 `cb4b2f872c670959258a7955cee47d6792fd756e708a6caf34884e21f79c9327`、変更後 `7eac16a0d336956a91d6593b9848779887bcfa5e815661d63ae7691caca61bdc`。
- `bash benchmarks/version-check-concurrency/measure.sh <実装名> <depup> 5` を before-a → after-a → after-b → before-b の順に実行しました (各シナリオ 1 実装 10 回)。`--dry-run` で、既定の age (1 週間) と OSV の確認を有効にしています。
- シナリオ: `sixty` は crates.io の 60 件 (更新候補ごとに OSV を問い合わせる)、`workspace` は同じ 60 件を 15 件ずつ 4 つのメンバーに分けた Cargo workspace、`npm` は npm の 30 件、`depup-own` は depup 自身の Cargo.toml (すべて最新で OSV を問い合わせない対照)。
- ネットワークとレジストリ・OSV の状態に左右されます。測定中はビルドやテストを並行して動かしていません (GitHub の CI の待ち合わせだけを並行しました)。Windows の depup は `HOME` ではなく利用者のプロファイルからグローバル設定を読むため、変更前後とも同じ利用者の設定で測っています。

## 結果

時間は 10 回の中央値 (括弧は最小〜最大)、単位は秒です。生データは [before-a](before-a.csv)・[after-a](after-a.csv)・[after-b](after-b.csv)・[before-b](before-b.csv)、まとめは [comparison.csv](comparison.csv) です。

| シナリオ | 変更前 | 変更後 | 短縮率 | 前後の範囲 |
|---|---:|---:|---:|---|
| sixty | 6.737 (6.230〜11.562) | 2.575 (2.227〜5.209) | 61.78% | 重ならない |
| workspace | 6.996 (6.619〜7.832) | 3.143 (2.551〜4.551) | 55.07% | 重ならない |
| npm | 5.719 (5.339〜6.349) | 3.558 (3.283〜7.034) | 37.78% | 重なる (変更後の 1 回が 7.034 秒) |
| depup-own | 0.799 (0.694〜3.680) | 0.960 (0.562〜1.795) | -20.21% | 重なる |

対照の `depup-own` は中央値が遅く見えたため、同じ実行ファイルで before → after → after → before を 2 巡、各実装 20 回測り直しました ([control.csv](control.csv))。中央値は 0.734 秒 (0.660〜1.153) → 0.677 秒 (0.595〜1.018) で範囲が重なり、退行は見られませんでした。上の -20.21% は少ない回数のばらつきと判断しています。

探索段階では、上限を環境変数で変えられる実験用のビルド (コミットしていない) で 4・8・16・32 を各 2 回比べ、`sixty` の中央値は 4 で約 6.4 秒、8 で約 3.4 秒、16 で約 2.2 秒、32 で約 1.8 秒でした。16 から 32 の差は小さく、OSV への同時の問い合わせが増えるため、16 を採りました。`workspace` は 1 マニフェスト 15 件なので 16 と 32 は同じ設定ですが、2 回の測定で約 2 倍の差が出ており、この測定のばらつきの大きさを示しています。

## 判断

- 版の一覧の取得の同時実行数はレジストリ別のセマフォで変わらず、crates.io の API を使う場合の 1 リクエスト/秒もアダプタが守ります。増えるのは OSV (api.osv.dev) への同時の問い合わせで、1 マニフェストあたり最大 16 件です。マニフェストは今までどおり 1 つずつ処理します。
- 表示順は `futures::stream::buffered` の入力順のままで、出力は変わりません。
- CLI 全体の時間は、依存の数・更新候補の数・ネットワークの状態で大きく変わります。依存が少ないマニフェストや更新候補の無いマニフェストでは差がありません。
